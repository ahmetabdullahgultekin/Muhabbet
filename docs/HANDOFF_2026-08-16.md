# Handoff — 2026-08-15/16

Written for whoever picks this up next, human or agent, on a different machine. It is the context
that would otherwise have stayed in a chat window. Read it once before touching anything.

---

## 1. The situation, in one paragraph

Muhabbet's documentation described a nearly finished messenger. It is not one. Over two days a
design-system PR, a device test by the owner, and three audits established that **the app's UI was
largely written and the wiring behind it largely was not** — roughly twenty controls were drawn and
did nothing, one whole feature (calls) has never worked at all, and the app reported server failures
to the user as success. None of this was visible from the repo, because an empty `{}` handler and an
unoverridden interface default are both valid Kotlin, and **CI had never once built the mobile app**.
The owner found the first defects within minutes of installing a build on a real phone.

Twenty-two PRs were merged and twenty-six findings filed. The code is in materially better shape.
**None of it has been seen running.**

---

## 2. The single most important fact

**There is no emulator on this host and there cannot be one.** `/dev/kvm` is absent, `/proc/cpuinfo`
reports zero `vmx`/`svm` flags (no nested virtualisation on the VM), `emulator -list-avds` is empty
and the SDK has no `system-images/`.

Therefore: compilation, unit tests, and static analysis are the *only* verification available
server-side. Anything that is only true when a human looks at it — motion, layout, gesture, colour on
a real panel — **cannot be signed off here**. An earlier version of `CLAUDE.md` claimed an emulator
existed; that claim was false and is corrected.

Everything merged on 2026-08-15/16 is compiler-verified and test-verified. **Zero of it is
device-verified.**

## 3. Rules that came out of this, and why

These are not style preferences. Each one was learned by shipping the mistake.

**A. For anything user-visible, check three things: does it persist, does anything read it, and does
a mechanism exist.** Adding persistence alone to App Lock would make the toggle remember its
position while the app still never locks — strictly worse than leaving it visibly broken, because it
then looks repaired. Wallpaper had the same trap. Media quality needed both halves. Ask all three
questions before calling anything fixed.

**B. Failure that looks like success is the characteristic defect here.** `ApiClient` ignored the
HTTP status, so a 403 decoded cleanly to `data = null` and surfaced as "you have nothing yet" or a
success toast. Communities looked empty when it was actually erroring. Broadcast lists have 404'd
since they were written and nobody knew. Fixed in #374 — but the same *shape* recurs: a gate that
does not run reads as a gate that passed. Mobile CI's `pull_request` trigger did not watch its own
workflow file, so a PR changing it produced zero checks, which on the PR page is indistinguishable
from "nothing to run".

**C. A red CI check here is usually environmental.** Before blaming a branch, run the same workflow
against `main`. Five checks were red for months for reasons that had nothing to do with any code.

**D. Do not trust a report — including an agent's — without checking the load-bearing claim.**
Agents were right most of the time and wrong in ways that mattered: one asserted wallpaper had real
consumers (it did not; they were the picker reading back its own selection). Conversely, when I gave
an agent a list of 17 defects it verified them and rejected 4 with reasons, then found 6 more I had
missed. Both directions happen. Check the claim the decision rests on.

**E. Verify by measurement, not by the absence of an error.** A production `DELETE` was issued with
`docker exec` and no `-i`; psql got no stdin, exited silently, the command "succeeded", and nothing
was deleted. Counting the rows afterwards is what caught it.

## 4. What was done

**Correctness / security**
- `ApiClient` now throws on non-2xx, so server errors reach the user (#374). This was masking the
  true state of several other features.
- Community endpoints no longer serve strangers' data: members-only reads, `addGroup` authorised
  against the caller (an IDOR disclosing arbitrary conversation metadata), `addMember` restricted
  (#375). **Deployed.**
- Swipe-to-reply crashed the app — 0.3.0 replaced a clamped value with an under-damped spring that
  undershoots zero into a padding (#359).
- Placeholder E2E keys were written to production on every launch, for everyone, with encryption
  off; stopped, and the 2,802 junk rows deleted (#379).
- Removing a group from a community always threw — a `DELETE @Query` with no `@Modifying` (#360).
- Nineteen spinners kept turning ~4s after the work finished, because reporting blocked clearing
  them; six were on the ordinary success path (#390).

**Features that were missing entirely**
- Reach someone by phone number — previously the *only* way to contact anyone was to add them in the
  phone's address book first, and nothing said so (#389).
- Communities management: members, add, remove group, rename, leave (#376).
- Privacy settings that actually apply — the server was accepting two of them and ignoring them
  (#377, #382).

**Infrastructure**
- Mobile CI builds Android for the first time (#366). It needed `ANDROID_HOME`; the SDK was on the
  runner all along.
- `mobile-release.yml` builds and **signs** on a `v*` tag, and refuses to publish if the signing
  certificate is not `e848…3560`. Needs four repo secrets that do not exist yet — see §6.
- `CLAUDE.md` corrected (#384): its "DONE" list meant "code was written", never "seen working".

## 5. Check these on a phone, in this order

1. **Long-press a message containing a link** and confirm reply / forward / delete still appear.
   Links became separately tappable in 0.3.3 and Android dispatches gestures child-first. This is the
   most likely regression in the whole batch, and it is a one-commit revert.
2. **Swipe-to-reply** — this crashed the app in 0.3.0. Confirm it is fixed.
3. **Buttons stop spinning** when the work finishes, not four seconds later.
4. **Start a chat with a number not in your contacts.**
5. **Communities**: open one, view members, rename, leave.
6. Predictive back (Android 14+) and the avatar handoff into the chat title — both from 0.3.0, never
   observed; watch for back skipping a screen, or a stray avatar when leaving a chat.

## 6. Environment facts that will otherwise cost an hour

- **The release keystore is not on the server.** It is on the owner's Windows machine under
  `C:\Users\ahabg\.keystores\`. Releases signed with anything else will not install as an update:
  the signer must be `CN=Muhabbet, O=Rollingcat Software`, SHA-256
  `e848191121876e08cc0968ae2a3c8591810add502e52e5d5dd1c8bb1f2aa3560`. The server can only produce
  unsigned artifacts. Test builds are signed with the CI debug key (`2817…dd07`) — those install over
  each other but never over a release build.
- **CI signing is one step from working**: add `MUHABBET_KEYSTORE_BASE64`, `MUHABBET_KEYSTORE_PASSWORD`,
  `MUHABBET_KEY_ALIAS`, `MUHABBET_KEY_PASSWORD` as repo secrets, then
  `gh workflow run "Mobile Release" -f tag=v0.3.3`. Caveat, stated plainly: the runner is the
  production server, so the key is briefly on that box during a release build.
- **SSH to GitHub from the server is read-only.** Push with
  `git -c credential.helper='!gh auth git-credential' push https://github.com/ahmetabdullahgultekin/Muhabbet.git <branch>`.
- **Prod OTPs cannot be read from the log** — `SMS_PROVIDER=twilio-verify`; the log shows only the
  last four digits of the number. The documented test numbers are unallocated, so you cannot log in
  as a test user against production. Mint a JWT with `JWT_SECRET` (needs `iss: "muhabbet"`) instead.
- **Deploy is `--env-file .env.prod` with the repo-root compose file**, and tag the running image as
  `rollback-<date>` first. Latest rollback tag: `muhabbet-muhabbet-backend:rollback-2026-08-16b`.
  Deploy is gated on Backend CI succeeding, which is red for environmental reasons, so it does not
  fire automatically — a backend change requires a manual deploy.
- **Still-red CI checks, all environmental**: iOS (no macOS runner is ever assigned), backend tests
  (Testcontainers cannot reach the password-protected shared Redis; ~18 failures reproduce on clean
  `main`), detekt (compiled against Kotlin 2.0.21, running 2.4.10 — issue #279), gitleaks (a stale
  `/tmp/gitleaks.tmp` on the runner).
- Disk on the host runs at ~93–95%. Check `df -h /` before a Docker or Gradle build.

## 7. Open work, and what actually blocks it

Tracked as GitHub issues — that is the inventory, not this file. `gh issue list -R ahmetabdullahgultekin/Muhabbet`

**Needs a decision, not code:**
- **Calls (#367–#373)** — three independent fatal breaks. The client never sends `call.initiate`, no
  microphone track is ever published, and LiveKit is not configured in production so the NoOp bean
  runs. Fixing the code is pointless until someone decides where LiveKit comes from: self-hosted on
  an already-strained box, LiveKit Cloud, or hide the feature until it is real.
- **#393** — chat folders, backups and the bot platform are complete server-side features with zero
  mobile callers. Wire them or remove them. Backups is listed as a trust-and-security feature, so a
  user could reasonably believe their messages are backed up when nothing ever calls the endpoint.

**Real work, no blocker:**
- **#378 App Lock** — needs an actual lock: a lifecycle gate plus biometric or PIN. There is no
  biometric dependency in the build at all. `TwoStepSetupScreen` is the model to copy; it is fully
  wired.
- **#380 Wallpaper** — a complete backend vertical (`chat_wallpapers`, `/api/v1/wallpapers`) sits
  unused while the picker writes to a sink and `ChatMessageList` hardcodes the theme default.
- **#387 Invite flow** — community membership currently derives from group membership, which is a
  restriction standing in for consent.
- **#363 image viewer**, **#381 transcription** (crashes on Android 8–11 and opens the live mic
  above), **#361/#362 follow-ups**.

## 8. Two things I got wrong, recorded so they are not repeated

**I attached an unsigned APK to a release the owner could download.** It cannot install — Android
reports "package appears to be invalid" — and he hit exactly that. Naming the file `-unsigned` and
writing a warning in the notes was not enough. Build artifacts that cannot be installed should not
sit next to ones that can.

**I merged the design-system PR calling it verified, and it contained a crash on a common gesture.**
The tests were green and the commit messages were excellent; neither covers a spring undershooting
into a padding. When a change is about motion and nothing can observe motion, "verified" is the wrong
word — say what was checked and what was not.
